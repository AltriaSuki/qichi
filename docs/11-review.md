## 一、结论

- **阶段**：功能上已完善（第 0–10 阶段全部完成、已部署、有内置更新、CI 三端通过）；但失败路径和长期运行还有原型级的缺口——会**静默丢数据**、**静默断同步**、**任务永久卡死**、**备份撑满磁盘**。所以处在「两人试用（beta）」，还不是可以放心长期托付数据的生产可用。
- **代码质量中上**：同步内核、鉴权、真实数据库上的集成测试都明显好于一般个人项目；问题集中在「出错时」和「长期运行」，不在日常功能。

## 二、整体模型

| 层 | 位置 | 职责 |
|---|---|---|
| 共享 | `shared/` | 接口数据类、枚举、校验规则、UUIDv7、Diff 与署名、标签 |
| 服务端内核 | `server/…/db`（`RoomWriter`、`EntityWrites`、`Tx`）、`sync/`、`plugins/` | 事务、seq 与 change_log、提交后广播、错误格式、鉴权 |
| 服务端业务 | 约 20 个 `*Service` + `*Routes` | 业务规则（Service 直接写 SQL，没有独立的 Repository 层） |
| 任务与 AI | `jobs/JobQueue`、`ai/*` | PostgreSQL 任务队列、模型网关、房间资料检索、提示词 |
| 推送 | `push/*`、`RealtimeHub` | 通知决策、经实时通道的内置通知、备选 ntfy |
| 客户端内核 | `core/sync`、`core/database`、`core/network`、`core/auth` | 本地库（单表 JSON）、发件箱、拉取、令牌 |
| 客户端数据与界面 | `core/data/*Repository`、`feature/*` | 各功能读写与页面 |

核心调用链：

- **写**：界面 → Repository → `LocalStore.writeLocal`（一个 Room 事务：本地行 PENDING + 发件箱）→ `OutboxWorker` → `OutboxProcessor`（一次一条）→ `ApiClient`（401 自动刷新）→ Service（校验成员、锁房间行、幂等、`RoomWriter.change` 分配 seq 并写 change_log）→ 提交后 `RealtimeHub` 广播、`PushService` 决定通知 → 响应回来本地改 SYNCED。
- **读**：WebSocket `changed` → `SyncEngine.pullIfBehind` → `GET sync?since` → `SyncService.sync`（取一页 change_log、同实体留最后一次、读当前状态、可见性过滤）→ Room 事务写入 → Flow → 界面。
- **AI**：`POST ai/…` → `ai_jobs` + `jobs`，立即 202 → 后台检索房间资料、拼提示词、流式调用 → `ai.delta` → 写结果实体 → `ai.done`。

## 三、做得好的地方（保持）

1. 文档即规约、有决策记录；`openapi.yaml` 的 115 条路径与路由一一对应；枚举有契约测试。
2. 同步内核：房间行锁让 seq 连续无空洞；可重复读快照；`Tx.afterCommit` 提交后才广播；创建幂等；软删除语义统一。
3. 客户端离线优先的核心规则正确：服务端数据不覆盖 PENDING / FAILED / CONFLICT 的本机内容；文稿冲突不丢草稿；消息按不变的 createdSeq 排。
4. 安全基线：Argon2id、刷新令牌轮换与重复使用检测、每个请求核对登录是否有效、非成员 404、按文件头识别上传、路径越界检查、推送地址白名单、日志不打印正文与令牌、令牌 Tink 加密、容器非 root、端口只绑 127.0.0.1。没有发现 SQL 注入、命令注入、路径穿越。
5. 测试有分量：服务端 40 多个测试文件跑真实 PostgreSQL，`05-sync-offline.md` 第 5 节的必测项齐全；客户端发件箱、同步、刷新有 MockEngine 测试；CI 跑三端测试和 lint。
6. 分层纪律：`feature` 之间零引用；没有 TODO / FIXME / 空实现残留。

## 五、结构性问题详述

### S1 登录被动失效时清空整个本机库

- **位置**：`core/auth/SessionManager.kt:57-60`（收到失效就 `clearLocal()`）、`di/SyncModule.kt:238`（`clearAllTables()`：实体、发件箱、草稿、版本缓存）；服务端 `auth/AuthService.kt:138-141`（旧刷新令牌再用一次 → 整组作废）；`core/network/ApiClient.kt:121-123`（刷新网络失败只返回 null）。行为被 `ApiClientTest.kt:179` 固定为预期。
- **何时暴露**：弱网下刷新请求「服务端已轮换、响应没回来」；被踢、改密码、60 天没打开；Keystore 密钥丢失后重新登录（`signIn` 也清库）。推测：OkHttp 的 `retryOnConnectionFailure` 可能自动重发同一个刷新请求，放大概率。
- **影响**：离线攒下的消息、修改、未保存的文稿全部永久消失且无提示，违背 05 文档「本地内容在用户确认前绝不丢弃」。
- **修复（人类 2026-09-26 选定）**：服务端刷新令牌 **5 分钟宽限**（被换掉的旧令牌 5 分钟内再出现、它的后继还没被轮换过 → 换发新令牌，不作废登录）；客户端被动失效只清令牌、**保留本机数据**，本机数据记归属账号，同一账号登录后继续发送，换账号时先提示有多少条未发出、确认后再清。

### S2 没有新旧版本兼容

- **位置**：`shared/…/api/Sync.kt:19`（`Change.type` 是严格枚举）、`shared/…/api/Json.kt`（不容忍未知枚举值）、`core/sync/SyncEngine.kt:111-115`（整页解码）；拉取异常在 `RealtimeClient.handle`、`QichiApplication.pullAll` 被吞；服务端不看 `X-Qichi-Client`。
- **何时暴露**：下一次新增实体类型或枚举取值，服务端先部署、App 还没更新（第 3–10 阶段加了 25 种实体）。
- **影响**：旧 App 的 lastSeq 永远停住，对方的新消息、心情都收不到，界面没有任何提示。
- **修复**：客户端逐条宽松解码，不认识的跳过但记下来，升级后自动重新快照；服务端按版本头返回 `upgrade_required`（最低版本可配置）。

### S3 任务队列：单工作者、重启卡死、AI 出错不收尾

- **位置**：`jobs/JobQueue.kt:113`（一个工作协程）、`:173,186`（只在启动时回收锁定超过 10 分钟的）、`:97`（停机时 `release` 在已取消的协程里执行不了）；`ai/AiService.kt` 六个处理函数只捕获服务商异常；`ai/Prompts.kt:16`（替换后在全文里检查 `{{词}}`）；`feature/chat/ChatViewModel.kt:513`（无上限轮询）。
- **影响**：部署时正在跑的任务永远「执行中」——审稿预览永远生成中、问 AI 永远在转；聊天里出现 `{{name}}` 这样的文字会让所有问 AI 失败并卡住；长的预览任务阻塞问 AI。
- **修复**：周期回收、停机释放不可取消、AI 兜底标失败、提示词单次替换、客户端等待上限（P13-03）；按种类分通道（P13-14）。

### S4 发件箱：坏请求堵死队列、刷新失败被当永久失败

- **位置**：`core/sync/OutboxProcessor.kt:56-60`（5xx 停止本轮，无上限）、`:88-104`（401 不可重试：文稿保存直接删，其它标失败）；`ApiClient.kt:121-123,184`。
- **影响**：一条持续 500 的请求让后面所有消息永远「待发送」；令牌过期后刷新超时，好好的操作被标「发送失败」，文稿保存被悄悄丢掉。
- **修复（人类选定 24 小时）**：从第一次服务器错误算起 24 小时后标 FAILED、队列继续（断网不计入）；401 且令牌仍在时稍后重试；记录最近一次同步错误供界面显示。

### S5 备份撑满磁盘、日志不轮转、无异地与告警

- **位置**：`deploy/backup.sh:27`（每天全量打包文件卷、留 14 份）、`deploy/docker-compose.yml`（无 `logging`）、`07-deploy.md` 第 7 节（异地副本交给人类）。
- **影响**：文件卷 N GB → 备份 14×N GB，一年内很可能占满 20GB 的盘，PostgreSQL 写不了就停服务；备份和原数据在同一台机器。
- **修复**：去重增量备份（restic）并推到异地、日志轮转、磁盘超过 80% 推送告警；在 VPS 上执行由人类确认。

### S6 同步规则散落

- **已出现的 bug**：彻底删除计划时，`todos.plan_id` 靠外键 `ON DELETE SET NULL`（`V5__todo_plan.sql:147`）静默置空、不写 change_log（`trash/TrashService.kt:308-316`），两台手机上的待办一直指向不存在的计划。
- **规则复制**：未揭晓答案、未共享标注、对方已读位置、撤回内容的过滤分别写在 `SyncService`（两处）、`ExportService`、`TimelineService`、`QnaService.today` 和 AI 的资料收集里。
- **扩展成本**：新增一种同步实体约改 18 个文件（以 `DocComment` 为例）。
- **默认不安全**：`db/EntityWrites.kt:71` 只按 id 更新，是否属于本房间全靠调用方先查（现有调用方都查了）。
- **修复**：P13-11（完整性 + 按房间限定）、P13-12（可见性规则集中）、P13-13（实体登记表 + 覆盖测试）。

## 七、测试体系

## 十、长期维护视角：最可能后悔没早处理的事

1. **本机数据会被整个清空（S1）**——被测试写成了预期，没人会当它是 bug，直到丢了一封写了一晚上的信。
2. **新旧版本兼容（S2）**——开发时两端总一起更新，永远复现不了；真实使用中必然发生，表现只是「对方好像不说话了」。
3. **备份与磁盘（S5）**——前几个月一切正常，发现时往往服务器已经停了，而最近 14 份备份都在同一台机器上。
4. **发布链的两个单点**——正式签名钥匙只在一台电脑上（丢了只能卸载重装，本机未同步数据一起没了）；版本号依赖 git 历史（Q13）。
5. **规约只靠 AI 记住**——关键规则没有自动化守护，已经出现漂移。把最重要的几条变成测试或 lint，让违反时直接失败。
6. **后台常驻连接的安全边界（Q2）**——丢手机一年也许一次，一次就是全部聊天内容。
